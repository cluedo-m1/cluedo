## 1. Idéation

### Besoin
Le joueur doit pouvoir déterminer si un suspect a physiquement pu se déplacer entre deux lieux du campus dans le temps écoulé entre deux observations.

Ce problème est difficile à résoudre manuellement, car le chemin le plus court peut passer par plusieurs bâtiments intermédiaires. Le joueur doit donc pouvoir s'appuyer sur un calcul automatique de la durée minimale du trajet pour repérer les déplacements impossibles.
### Scénarios d'usage
- En tant que joueur ou joueuse, j'explore la carte du campus et les déplacements horodatés des suspects afin de repérer les impossibilités physiques de trajet.

- En tant que joueur ou joueuse, je compare deux observations d'un même suspect afin de savoir s'il a eu suffisamment de temps pour rejoindre le lieu suivant.

### Modèle
Le modèle repose sur un graphe représentant le campus :

- Lieu (Sommet) : représente un bâtiment du campus (BU, amphi, laboratoire, restaurant, etc.).
- Connexion (Arc) : représente un déplacement possible d'un lieu vers un autre, avec une durée associée en minutes.
- Observation : représente la présence d'un suspect dans un lieu à un instant précis.
- Suspect : entité à laquelle sont associées les différentes observations.

Entité pivot : le suspect, car on analyse ses observations successives pour vérifier la cohérence de ses déplacements.

Invariants (règles toujours vraies) :

- Les durées des connexions sont strictement positives.
- Chaque observation possède un lieu et un horodatage.
- Un déplacement est impossible si la durée minimale du trajet est supérieure au temps écoulé entre deux observations.
- Si les deux observations concernent le même lieu, le déplacement est considéré comme possible.
- Si aucun chemin ne relie les deux lieux, le déplacement est impossible.

### Algorithme
Algorithme choisi : Dijkstra avec une file de priorité (PriorityQueue en Java).

Dijkstra permet de calculer le chemin le plus court entre deux lieux en tenant compte des durées différentes de chaque connexion.

Principe :
- On initialise la distance du lieu de départ à 0 et celle des autres lieux à l'infini.
- On sélectionne le lieu non traité ayant la distance la plus faible grâce à une file de priorité.
- On actualise les distances des lieux voisins si un chemin plus court est trouvé.
- On répète jusqu'à atteindre le lieu d'arrivée ou jusqu'à ce qu'il n'y ait plus de chemin possible.
- On compare la durée minimale calculée avec le temps écoulé entre les deux observations.

Exemple :

Pour aller de la BU au laboratoire :
BU → Amphi : 4 min,
BU → Resto : 2 min,
Resto → Amphi : 1 min,
Amphi → Labo : 3 min,
Resto → Labo : 7 min

Si un suspect est vu à la BU à 14h00 puis au laboratoire à 14h05, le déplacement est impossible car il faudrait au minimum 6 minutes.

Complexité :
- Temps : O((V + E) log V), avec V le nombre de lieux et E le nombre de connexions.
- Mémoire : O(V + E) pour stocker le graphe, les distances et la file de priorité.

Alternatives écartées :
- BFS (parcours en largeur) : ne tient pas compte des durées différentes entre les connexions. Il compte les arêtes et non le temps réel.
- Floyd-Warshall : calcule les plus courts chemins entre toutes les paires de lieux. Il est moins adapté à notre besoin et possède une complexité en O(V³).

Dijkstra est donc le meilleur compromis pour notre fonctionnalité, car il calcule efficacement le temps minimal d'un déplacement entre deux lieux avec des durées positives.

### Impact sur les couches
- **BD** : migration `V4__graphe_campus.sql`
- **Back** : module `campus`
- **API** : API REST : `GET /api/v1/campus/graphe` (la carte) ; `GET /api/v1/campus/trajets/verification?depart=…&arrivee=…&duree=…` (le trajet est-il possible ?) ; codes : 200 si OK, 400 si la requête est invalide, 404 si un bâtiment n'existe pas
- **Front** : carte du campus et vérification d'un trajet

### Critères d'acceptation
- [ ] Règle principale : le trajet est impossible si la durée minimale nécessaire est supérieure au temps écoulé entre les deux observations.
- [ ] Égalité : si la durée minimale est égale au temps disponible, le trajet est considéré comme possible.
- [ ] Même lieu : si les deux observations ont lieu au même endroit, le déplacement est considéré comme possible.
- [ ] Absence de chemin : si aucun chemin ne relie les deux lieux, le trajet est considéré comme impossible.
- [ ] Requête invalide : si un paramètre est manquant ou si la durée est négative, l'API répond 400.

### Limites connues
- Les lieux sont des bâtiments, pas des salles : c'est plus simple pour une première version, les salles pourront venir plus tard.
- La vitesse : on suppose que les suspects se déplacent à une vitesse normale et régulière, sans prendre en compte les accélérations, les sprints ou les pauses.
- Les arcs : le graphe est orienté dans le code (chaque connexion va d'un lieu vers un autre), mais les données du campus ont pour l'instant une connexion dans chaque sens avec la même durée, car le campus ne comporte pas de sens unique.
