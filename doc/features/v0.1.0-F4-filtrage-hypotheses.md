## 1. Besoin et scénario d'usage

**Scénario d'usage (S2) :**
> En tant que joueur ou joueuse, je formule des hypothèses sur le suspect, le lieu et l'objet de l'incident. L'application met à jour dynamiquement la liste des possibles en éliminant les pistes incompatibles avec les indices déjà recueillis.

**Objectif métier :**
Au fil de l'enquête, le joueur active ou désactive les indices recueillis et sélectionne une hypothèse partielle ou complète sur `(suspect, lieu, objet)`. À chaque interaction, le système calcule :
1. Le **nombre total de scénarios complets encore compatibles** (`long`) avec l'ensemble des contraintes actives ;
2. Le **nombre de scénarios compatibles restants pour chaque valeur** (`long`) de chaque variable (permettant d'identifier les pistes éliminées à `0` et d'évaluer le poids combinatoire de chaque piste restante) ;
3. Le **nombre de nœuds explorés** (`long`) par le solveur (indicateur mesurable de l'efficacité de l'élagage).

---

## 2. Modèle du domaine

Le problème est modélisé comme un **problème de satisfaction de contraintes (CSP)** fini `P = (X, D, C)` en Java pur (aucune dépendance framework) :

- **Variables ordonnées `X = (X_0, ..., X_{n-1})`** : liste ordonnée et fixe de `n` dimensions d'enquête (`n >= 1`). Dans le Cluedo standard, `n = 3` avec `SUSPECT`, `LIEU`, `OBJET`.
- **Domaines finis `D = (D_0, ..., D_{n-1})`** : chaque variable `X_i` possède un ensemble ordonné et non vide de valeurs candidates `D_i`.
- **Littéral `L = (X_i, v, positif)`** : condition atomique portant sur la variable `X_i`, la valeur `v` dans `D_i` et un booléen `positif` :
  - `L` est **vrai** sous une assignation `sigma` si `sigma(X_i) = v` (cas positif) ou `sigma(X_i) != v` (cas négatif).
- **Contrainte logique (`ContrainteLogique`)** : représentée uniformément comme une **clause disjonctive de littéraux** `c = L_1 OU L_2 OU ... OU L_r` (`r >= 1`). Cette représentation unifiée exprime tous les indices de l'enquête ainsi que l'hypothèse du joueur :
  - *Exclusion simple* (`X_i != v`) : clause unitaire négative `[(X_i, v, false)]` ;
  - *Disjonction* (`(X_i = v_1) OU (X_j = v_2)`) : clause binaire positive `[(X_i, v_1, true), (X_j, v_2, true)]` ;
  - *Implication / incompatibilité* (`(X_i = v_1) => (X_j != v_2)`) : équivalente à `(X_i != v_1) OU (X_j != v_2)`, soit `[(X_i, v_1, false), (X_j, v_2, false)]` ;
  - *Hypothèse du joueur* (`X_i = v`) : clause unitaire positive `[(X_i, v, true)]` ajoutée dynamiquement pour chaque variable fixée par le joueur.
- **Validation à la construction (*fail fast*)** : toute tentative de construction avec un domaine vide, une variable inconnue, une valeur absente du domaine de sa variable ou une clause vide lève immédiatement une exception métier (`EnqueteInvalideException`).
- **Résultat du filtrage (`ResultatFiltrage`)** :
  - `totalScenariosCompatibles` (`long`) : nombre total de `n`-uplets satisfaisant toutes les clauses de `C` ;
  - `comptageParVariable` (`Map<VariableId, Map<ValeurId, Long>>`) : pour chaque variable et chaque valeur de son domaine initial, le nombre exact de scénarios compatibles contenant cette valeur (`0` signifie valeur éliminée) ;
  - `noeudsVisites` (`long`) : nombre de nœuds de l'arbre de recherche effectivement explorés.

## 3. Algorithme : énumération par retour arrière

### 3.1. Principe et pseudo-code

Avant le parcours, les clauses sont **pré-indexées par la profondeur maximale de leurs variables** (`clausesParProfondeur[p]`), où la profondeur d'une clause est le plus grand indice `i` parmi les variables apparaissant dans ses littéraux. Ainsi, à la profondeur `p`, on ne teste que les clauses qui deviennent entièrement assignées à ce niveau précis, sans jamais ré-évaluer les clauses déjà vérifiées aux profondeurs précédentes.

```text
FONCTION filtrer(variables[0..n-1], domaines, clauses):
    validerCoherenceEntrees(variables, domaines, clauses)
    clausesParProfondeur ← preIndexerParDerniereVariable(clauses, variables)
    compteurs ← initialiser à 0L pour chaque (var, val) de domaines
    totalSolutions ← 0L
    noeudsVisites ← 0L
    assignation ← tableau vide de taille n

    PROCEDURE explorer(profondeur):
        SI profondeur = n ALORS
            totalSolutions ← totalSolutions + 1L
            POUR i DE 0 À n - 1 FAIRE
                val ← assignation[i]
                compteurs[variables[i]][val] ← compteurs[variables[i]][val] + 1L
            FIN POUR
            RETOURNER
        FIN SI

        varCourante ← variables[profondeur]
        POUR CHAQUE val DANS domaines[varCourante] FAIRE
            noeudsVisites ← noeudsVisites + 1L
            assignation[profondeur] ← val

            SI toutesSatisfaite(clausesParProfondeur[profondeur], assignation) ALORS
                explorer(profondeur + 1)
            FIN SI
            // Sinon : coupure (élagage de tout le sous-arbre)
        FIN POUR
    FIN PROCEDURE

    explorer(0)
    RETOURNER ResultatFiltrage(totalSolutions, compteurs, noeudsVisites)
FIN FONCTION
```

### 3.2. Invariants

1. **Invariant d'assignation partielle** : à l'appel `explorer(profondeur)`, les variables `X_0, ..., X_{profondeur-1}` sont toutes assignées et satisfont toutes les clauses des niveaux `0` à `profondeur - 1`.
2. **Invariant d'évaluation unique** : le long d'une branche donnée, chaque clause `c` est évaluée au plus une fois (uniquement au niveau `p = max_{L dans c} indice(L.variable)`).
3. **Invariant de conservation des comptages** : pour toute variable `X_i`, la somme des compteurs de ses valeurs est toujours égale au total des solutions :
`pour tout i dans [0..n-1], somme_{v dans D_i} compteurs[X_i][v] = totalSolutions`.
4. **Invariant d'élagage** : le nombre de nœuds visités vérifie toujours :
`0 <= noeudsVisites <= somme_{i=0..n-1} (produit_{j=0..i} |D_j|)`.

### 3.3. Complexité en temps et en mémoire

Soit `n` le nombre de variables, `m = |C|` le nombre de clauses, `r` le nombre maximal de littéraux par clause et `d = max_i |D_i|` la taille maximale d'un domaine :

* **Complexité temporelle (pire cas sans élagage)** :
`O(d^n · (n + m · r))`
Le terme `d^n` correspond aux feuilles explorées, `m · r` à l'évaluation cumulée des clauses sur une branche et `n` à l'incrémentation des `n` compteurs par solution valide. Pour le Cluedo standard (`n = 3`, `d = 6`, soit `216` feuilles et `m <= 20`), l'exécution est inférieure à `1 ms`.
* **Gain par élagage (cas moyen)** : une clause unitaire sur la première variable `X_0` coupe un sous-arbre complet de taille `produit_{i=1..n-1} |D_i|` **pour chaque valeur exclue** du domaine `D_0`. De même, une clause binaire sur `(X_0, X_1)` coupe un sous-arbre de taille `produit_{i=2..n-1} |D_i|` pour chaque couple `(v_0, v_1)` incompatible.
* **Complexité spatiale** : `O(n + m · r + n · d)` en mémoire auxiliaire (pile d'appels de profondeur `n`, index des clauses `m · r` et table des compteurs `n · d`), sans matérialiser les `n`-uplets solutions en mémoire.

### 3.4. Alternative écartée et justification de non-trivialité

* **Produit cartésien complet filtré a posteriori (écarté)** : imbriquer trois boucles `for` et évaluer les contraintes uniquement sur les triplets complets. Cette approche est écartée car elle ne réalise **aucun élagage précoce** sur assignation partielle et **ne généralise pas à `n` variables** sans réécrire la structure de contrôle.
* **Justification de non-trivialité** : le solveur est paramétrable sur un nombre quelconque `n` de variables, pré-indexe des clauses logiques polymorphiques (exclusions, disjonctions, implications, hypothèses) par profondeur et mesure explicitement le gain d'élagage (`noeudsVisites`).

### 3.5. Limites connues (`v0.1.0`)

* **Pas de réduction préalable des domaines unaires** : en `v0.1.0`, une contrainte unitaire (ou une hypothèse du joueur) portant sur la variable d'indice `p` n'est évaluée qu'à la profondeur `p`. Si elle porte sur la dernière variable (`p = n - 1`), elle n'est évaluée qu'aux feuilles et ne réduit pas `noeudsVisites`. Une réduction initiale des domaines unaires avant la recherche est envisagée en `v0.2.0`.
* **Évaluation complète des clauses multi-variables** : une clause portant sur plusieurs variables n'est évaluée que lorsque sa dernière variable est assignée (pas de propagation unitaire anticipée sur les disjonctions à `r >= 3` littéraux, rôle dévolu au solveur AC-3 de F2).
* **Ordre fixe des variables** : les variables sont parcourues dans l'ordre déclaré par l'enquête sans réordonnancement dynamique (heuristique MRV).
- **Séquences PostgreSQL et jeu de démonstration** : le script `R__demo_filtrage_hypotheses.sql` insère des identifiants explicites. Sur PostgreSQL, les séquences `GENERATED BY DEFAULT AS IDENTITY` ne sont pas avancées automatiquement ; cela reste sans impact en `v0.1.0` car F4 n'expose aucun endpoint de création d'enquête.

## 4. Différence avec MindCrime

D'après son README (consulté le 24/11/2026), le projet *MindCrime* ne contient encore qu'un plan : sa feature D5 prévoit une « recherche d'hypothèses » avec « élimination des scénarios impossibles ». Son implémentation n'existant pas, nous ne comparons que ce que F4 apporte de vérifiable chez nous, au-delà d'une simple élimination de pistes :

1. **Dénombrement exact par valeur (`comptageParVariable`)** : pour chaque suspect, lieu ou objet non éliminé, le joueur voit exactement combien de scénarios complets restent compatibles avec cette valeur (permettant de distinguer une piste encore possible dans 1 seul scénario d'une piste présente dans 15 scénarios).
2. **Mesure de l'élagage (`noeudsVisites`)** : le solveur quantifie directement l'effet des indices sur l'espace de recherche en comparant les nœuds explorés à l'arbre complet.
3. **Généralité CSP à `n` variables et clauses composables** : le moteur n'est pas limité à 3 catégories figées et prend en charge des contraintes relationnelles (implications et disjonctions entre variables), pas uniquement des éliminations directes.

  - `adapter.out.persistence` : entités JPA et adaptateur PostgreSQL/H2 (`IllegalStateException` si une enquête en base est structurellement corrompue, par exemple un indice sans littéral).
- **API REST (`/api/v1/joueur/enquetes/{enqueteId}`)** :
  - `GET /api/v1/joueur/enquetes/{enqueteId}` : retourne les variables ordonnées, leurs valeurs et les indices (`id` et `libelle` uniquement, sans exposer les clauses logiques). Statuts : `200 OK`, `404 Not Found` (enquête inconnue), `500 Internal Server Error` sans détail technique si données corrompues en base, au format `application/problem+json` (RFC 9457).
  - `POST /api/v1/joueur/enquetes/{enqueteId}/filtrages` : ressource de calcul sans persistance recevant `{ "indicesActifsIds": [...], "hypothese": { ... } }` (`indicesActifsIds` obligatoire, `hypothese` facultative) et renvoyant `200 OK` avec :

    - `comptageParVariable` : **liste ordonnée** d'objets par variable (et non un objet JSON, afin de préserver l'ordre d'affichage même lorsque les codes ressemblent à des entiers),
    - `noeudsVisites` (`long`).
    Statuts d'erreur : `400 Bad Request` (`title: "Requête invalide"` pour indice inconnu, variable inconnue ou valeur hors domaine), `404 Not Found`, `415 Unsupported Media Type`, `500 Internal Server Error` (RFC 9457).
- **Front (Angular)** : écran minimal permettant de cocher les indices actifs, de choisir une hypothèse sur 3 listes déroulantes (`Suspect`, `Lieu`, `Objet`) et d'afficher le nombre total de scénarios compatibles ainsi que le décompte par valeur.

## 7. Critères d'acceptation et tests prévus

1. **Sans contrainte ni hypothèse** : `totalScenariosCompatibles` vaut le produit des tailles de domaines et chaque valeur `v` de `D_i` a un compteur égal au produit des tailles des autres domaines.
2. **Cas de référence chiffré (exclusion + implication)** : avec `suspect` dans `{A, B}`, `lieu` dans `{X, Y}`, `objet` dans `{1, 2}` et les contraintes `suspect != A` et `(lieu = X) => (objet != 1)`, le solveur retourne `totalScenariosCompatibles = 3`, `comptageParVariable = { suspect: {A: 0, B: 3}, lieu: {X: 1, Y: 2}, objet: {1: 1, 2: 2} }` et `noeudsVisites = 8` (contre 14 pour l'arbre complet).
3. **Hypothèse sur la dernière variable** : sur le même cas avec l'hypothèse `objet = 2`, le solveur retourne `totalScenariosCompatibles = 2`, `comptageParVariable = { suspect: {A: 0, B: 2}, lieu: {X: 1, Y: 1}, objet: {1: 0, 2: 2} }` et `noeudsVisites = 8`.
4. **Contradiction complète** : des contraintes incompatibles retournent `totalScenariosCompatibles = 0` et tous les compteurs à `0L`.
5. **Validation des entrées (*fail fast*)** : une valeur hors domaine ou une variable inconnue lève `EnqueteInvalideException`.
6. **Généralité (`n = 4`) et oracle** : sur 30 instances aléatoires à 4 variables, les résultats du backtracking sont strictement identiques à ceux d'un produit cartésien naïf, avec `noeudsVisites <= noeudsArbreComplet` partout et `noeudsVisites < noeudsArbreComplet` dès qu'une clause complète sur un préfixe élimine une branche non vide.
7. **Persistance et intégrité SQL (`EnquetePersistenceAdapterIT`)** : chargement respectant la colonne `ordre`, rejet par clé composite des valeurs hors domaine, suppression en cascade sur les 5 tables, et `IllegalStateException` si un indice en base ne contient aucun littéral.
8. **Architecture et API REST (`JoueurControllerIT`, `ArchitectureHexagonaleTest`)** : respect strict de l'hexagone, exposition OpenAPI des deux endpoints, masquage des clauses sur le `GET`, réponses `200`, `400`, `404`, `415` et `500` (sans fuite de détail technique) conformes RFC 9457.
