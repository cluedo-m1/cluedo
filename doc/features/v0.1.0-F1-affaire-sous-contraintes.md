## 1. Idéation

### Besoin

Le joueur souhaite pouvoir lancer de nouvelles enquêtes sans que
celles-ci soient entièrement prédéfinies manuellement.

La création manuelle d'une enquête est complexe, car elle nécessite
de vérifier la cohérence entre les suspects, les lieux, les horaires,
les moyens d'accès et les indices.

L'objectif est d'automatiser la génération d'enquêtes variées,
cohérentes et possédant exactement une solution, dans un environnement
universitaire fictif.

### Scénarios d'usage

- **En tant que joueur ou joueuse**, je lance une nouvelle enquête
  afin de disposer d'une affaire générée sous contraintes, vérifiée
  à solution unique et résoluble grâce aux indices fournis.

- **En tant que joueur ou joueuse**, je consulte les suspects,
  les lieux et les indices de l'enquête générée afin de commencer
  mon investigation.

### Modèle

L'entité pivot du projet est l'enquête.

Les principaux éléments du modèle métier sont :

- `Enquete` : représente une affaire générée et contient les
  éléments nécessaires à sa résolution.
- `Suspect` : représente une personne potentiellement responsable
  de l'incident, avec ses disponibilités et ses moyens d'accès.
- `Lieu` : représente un emplacement du campus et ses conditions
  d'accès.
- `Indice` : représente une contrainte structurée accompagnée
  d'une description textuelle compréhensible par le joueur.
- `Solution` : représente l'affectation complète et correcte
  des variables de l'enquête.
- `Horaire` : représente un créneau temporel.
- `MoyenAcces` : représente un moyen d'accès, par exemple un badge,
  une clé ou un accès libre.

Les quatre variables du problème sont :

- Le coupable.
- Le lieu de l'incident.
- L'heure de l'incident.
- Le moyen d'accès utilisé.

Chaque variable possède un domaine de valeurs possibles.

Les indices sont représentés sous une forme structurée :

- Variable concernée.
- Opérateur de comparaison.
- Valeur de référence.
- Description textuelle.

Exemple :

    Variable : COUPABLE
    Operateur : DIFFERENT
    Valeur : Emma
    Description : Emma n'était pas impliquée dans l'incident.

Les opérateurs envisagés pour cette version sont :

- EGAL
- DIFFERENT
- AVANT
- APRES

#### Invariants

- Une enquête valide possède exactement une solution.
- Le coupable appartient à la liste des suspects.
- Le lieu appartient aux lieux proposés dans l'enquête.
- Le suspect doit être présent sur le campus à l'heure retenue.
- Le moyen d'accès doit être compatible avec le suspect et le lieu.
- Tous les indices doivent être compatibles avec la solution.
- Les domaines des variables ne doivent pas être vides.
- La solution secrète ne doit pas être exposée au joueur.

Les invariants structurels sont vérifiés lors de la construction
des objets métier.

Les contraintes de cohérence sont vérifiées par l'algorithme
de génération.

L'unicité est vérifiée par le moteur de déduction de la feature F2
avant l'enregistrement de l'enquête.

### Algorithme

#### Principe

La génération repose sur un problème de satisfaction de contraintes
(CSP), résolu à l'aide d'un algorithme de backtracking.

Un CSP est défini par un ensemble de variables, leurs domaines
de valeurs et les contraintes qui doivent être respectées.

Le backtracking construit progressivement une affectation des
variables. Lorsqu'une affectation partielle viole une contrainte,
l'algorithme abandonne cette branche et revient au choix précédent.

L'ordre d'exploration des valeurs peut être mélangé à l'aide
d'un générateur pseudo-aléatoire afin de varier les enquêtes.

Une graine fixe permet de reproduire une génération dans les mêmes
conditions.

Une fois une solution cohérente trouvée, des indices compatibles
avec celle-ci sont construits et ajoutés progressivement.

Le moteur de déduction de la feature F2 vérifie le nombre de
solutions compatibles avec les indices et les contraintes
accessibles au joueur.

La solution secrète n'est pas transmise au solveur comme
contrainte de résolution.

L'enquête est validée uniquement si le solveur identifie exactement
une solution correspondant à la solution générée.

#### Pseudo-code du backtracking

    rechercherSolution(affectation):

        Si toutes les variables sont renseignées :
            Retourner l'affectation valide

        Choisir une variable non renseignée

        Pour chaque valeur de son domaine :

            Affecter la valeur à la variable

            Si les contraintes applicables sont respectées :

                Rechercher récursivement une solution

                Si une solution est trouvée :
                    Retourner cette solution

            Annuler l'affectation de la variable

        Retourner un échec

#### Pseudo-code de la génération

    genererEnquete(graine):

        Initialiser les domaines et les contraintes

        Initialiser le générateur pseudo-aléatoire

        Mélanger l'ordre des valeurs des domaines

        Rechercher une solution par backtracking

        Si aucune solution n'existe :
            Signaler un échec de génération

        Construire des indices compatibles avec la solution

        Initialiser une liste d'indices vide

        Tant que des indices candidats restent disponibles :

            Ajouter un nouvel indice

            Demander au solveur de vérifier les solutions

            Si aucune solution n'existe :
                Signaler une incohérence

            Si exactement une solution existe
            et correspond à la solution générée :
                Construire et retourner l'enquête

        Signaler un échec de génération

La génération doit être bornée afin d'éviter une boucle infinie
lorsqu'aucune enquête valide ne peut être construite.

#### Exemple de déroulement

Considérons les domaines suivants :

- Suspects : Alice, Thomas, Emma, Lucas.
- Lieux : bibliothèque, secrétariat, salle informatique.
- Horaires : 9 h, 10 h, 11 h.
- Moyens d'accès : badge, clé, accès libre.

Sans contraintes, le nombre de combinaisons possibles est :

    4 x 3 x 3 x 3 = 108

Supposons que Thomas possède un badge, mais pas de clé,
et qu'il soit absent du campus à 9 h.

L'algorithme sélectionne Thomas comme suspect potentiel,
puis le secrétariat comme lieu.

Le secrétariat nécessitant une clé, cette affectation est
incompatible. L'algorithme revient au choix du lieu et
sélectionne la salle informatique, accessible avec un badge.

Il essaie ensuite l'horaire de 9 h. Thomas étant absent,
cet horaire est rejeté.

L'algorithme essaie alors 10 h. Si Thomas est présent et que
les autres contraintes sont respectées, une solution possible
est obtenue :

    Coupable : Thomas
    Lieu : Salle informatique
    Heure : 10 h
    Moyen d'accès : Badge

Des indices compatibles avec cette solution sont ensuite
générés jusqu'à ce que le moteur de déduction confirme
son unicité.

#### Complexité

Soit n le nombre de variables et d la taille maximale
de leurs domaines.

Dans le pire des cas, le backtracking explore un nombre
exponentiel d'affectations.

Complexité temporelle du backtracking :

    O(d^n)

Cette complexité ne comprend pas le coût de vérification
des contraintes.

Complexité spatiale auxiliaire :

    O(n)

Elle correspond à la profondeur maximale de la récursion
et à l'affectation courante, hors stockage des domaines,
des contraintes et des indices.

La génération complète comprend également la construction
des indices et les appels au moteur de déduction.

Si k indices sont ajoutés et que T_solveur représente le coût
d'un appel au solveur, le coût des vérifications d'unicité
est majoré par :

    O(k x T_solveur)

Le backtracking permet de réduire l'espace effectivement
exploré en éliminant les branches incompatibles avant
d'avoir renseigné toutes les variables.

#### Structures de données envisagées

- Listes pour représenter les domaines des variables.
- Map pour représenter les affectations partielles.
- Ensembles pour représenter les moyens d'accès autorisés.
- Liste pour stocker les contraintes et les indices.
- Enumérations pour représenter les variables, les moyens
  d'accès et les opérateurs de comparaison.

Les objets valeur seront immuables lorsque cela est possible.

#### Alternatives écartées

Tirage aléatoire simple :

Cette approche consiste à sélectionner indépendamment les
valeurs des variables, puis à vérifier leur cohérence.

Elle est écartée car elle peut générer de nombreuses
combinaisons invalides et nécessiter plusieurs tentatives.

Recherche exhaustive :

Cette approche consiste à énumérer toutes les combinaisons
complètes avant de vérifier les contraintes.

Elle est écartée comme algorithme principal car elle ne
permet pas d'éliminer suffisamment tôt les branches
incompatibles.

Elle pourra néanmoins servir de référence dans les tests
sur de petits domaines.

Génération d'un ensemble minimal d'indices :

Cette optimisation n'est pas retenue pour la première version.
Elle sera étudiée dans la feature prévue pour la v0.2.0.

### Impact sur les couches

- **BD** : création d'une migration Flyway dédiée à la
  persistance des enquêtes, des solutions et des indices.
  Le numéro de migration et le schéma commun seront
  définis avec l'équipe.

- **Back** : création d'un module `generation` respectant
  l'architecture hexagonale :

  - `domain` : modèle métier, contraintes et backtracking.
  - `application` : cas d'utilisation, services et ports.
  - `adapter/out/persistence` : persistance avec JPA.
  - `adapter/in/web` : contrôleur REST et DTO.
  - `config` : assemblage Spring Boot.

  La communication avec le moteur de déduction F2 sera
  réalisée à travers un port, sans dépendance directe
  à ses adaptateurs ou à ses tables.

- **API** : proposition d'un endpoint :

      POST /api/v1/enquetes

  Codes de retour envisagés :

  - 201 Created : enquête générée et enregistrée,
    avec un en-tête Location.
  - 400 Bad Request : paramètres invalides.
  - 422 Unprocessable Content : paramètres valides,
    mais aucune enquête cohérente ne peut être générée.

  La réponse contient les informations nécessaires au joueur,
  mais ne contient pas la solution secrète.

  Les erreurs sont retournées au format problem+json.

- **Front** : ajout d'un bouton permettant de lancer une
  nouvelle enquête et d'un écran affichant les suspects,
  les lieux, les horaires, les moyens d'accès et les indices.

### Critères d'acceptation

- [ ] Le joueur peut demander la génération d'une nouvelle enquête.
- [ ] La solution générée respecte toutes les contraintes métier.
- [ ] Tous les indices sont compatibles avec la solution secrète.
- [ ] Chaque enquête générée possède exactement une solution.
- [ ] Une enquête valide est enregistrée en base de données.
- [ ] La solution secrète n'est pas exposée au joueur par l'API.
- [ ] L'algorithme gère le cas où aucune solution n'existe.
- [ ] La génération peut être reproduite avec une graine aléatoire fixe.

### Limites connues

- Les enquêtes reposent initialement sur quatre variables
  et des domaines de taille limitée.
- Les types de contraintes et d'indices sont limités
  dans cette première version.
- La génération ne garantit pas encore un nombre minimal
  d'indices.
- La difficulté des enquêtes n'est pas encore contrôlée.
- La génération ne garantit pas que deux enquêtes successives
  seront nécessairement différentes.
- Le backtracking possède une complexité exponentielle
  dans le pire des cas.
- L'intégration finale de la vérification d'unicité dépend
  du contrat défini avec le moteur de déduction F2.

La réduction du nombre d'indices sera étudiée dans la v0.2.0.

La génération à difficulté cible sera étudiée dans la v1.0.0.
