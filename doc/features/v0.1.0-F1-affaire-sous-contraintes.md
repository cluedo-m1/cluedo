
# F1 : Affaire tirée sous contraintes

## 1. Idéation

### Besoin

Automatiser la génération d'enquêtes cohérentes et variées,
possédant exactement une solution, dans un environnement
universitaire fictif.

La création manuelle est complexe car elle nécessite de vérifier
la cohérence entre les suspects, les lieux, les horaires,
les moyens d'accès et les indices.

### Scénarios d'usage

- En tant que joueur, je génère une nouvelle enquête afin de
  disposer d'une affaire à résoudre.
- En tant que joueur, je consulte les suspects, les lieux et
  les indices afin de mener mon investigation.

### Modèle

L'entité pivot est `Enquete`.

| Élément | Rôle |
|---|---|
| Enquete | Regroupe les données de l'affaire |
| Suspect | Personne, autorisations et horaires de présence |
| Lieu | Emplacement et conditions d'accès |
| Indice | Contrainte accompagnée d'une description |
| Solution | Affectation correcte des quatre variables |
| Horaire | Créneau temporel |
| MoyenAcces | Badge, clé ou accès libre |

Les quatre variables du CSP sont le coupable, le lieu,
l'horaire et le moyen d'accès.

Un indice contient une variable, un opérateur, une valeur
et une description. La génération utilise l'opérateur `DIFFERENT`.

#### Invariants

- La solution appartient aux domaines proposés.
- Le coupable est présent à l'heure de l'incident.
- Le moyen d'accès est compatible avec le suspect et le lieu.
- Tous les indices sont compatibles avec la solution.
- Chaque enquête générée possède exactement une solution.
- La solution secrète n'est pas exposée par l'API.

Les contraintes sont vérifiées dans le domaine métier.
L'unicité est contrôlée avant la persistance.

### Algorithme

#### Principe

Le backtracking affecte progressivement une valeur à chaque
variable. Lorsqu'une contrainte n'est pas respectée, il abandonne
la branche et revient au choix précédent.

L'ordre des valeurs est mélangé à l'aide d'une graine
pseudo-aléatoire (seed), permettant de reproduire une génération.

Une fois la solution trouvée, des indices sont construits
pour éliminer les valeurs alternatives. Un vérificateur
indépendant de la F2 contrôle l'unicité de la solution.

#### Pseudo-code

    rechercherSolution(affectation):
        Si toutes les variables sont renseignées :
            Retourner la solution

        Pour chaque valeur de la variable suivante :
            Affecter la valeur

            Si les contraintes sont respectées :
                Rechercher récursivement une solution
                Si une solution est trouvée :
                    Retourner la solution

            Annuler l'affectation

        Retourner un échec

La génération complète suit les étapes suivantes :

1. Valider et mélanger les domaines.
2. Rechercher une solution par backtracking.
3. Générer les indices compatibles.
4. Vérifier qu'il existe exactement une solution.
5. Enregistrer et retourner l'enquête.

Si aucune solution valide n'est trouvée, la génération échoue.

#### Exemple

Avec quatre suspects, trois lieux, trois horaires et trois
moyens d'accès, il existe initialement 108 combinaisons.

Thomas possède un badge mais pas de clé. Le backtracking
rejette donc le secrétariat, qui nécessite une clé.
Il rejette également 9 h si Thomas est absent à cet horaire.

Une solution possible est :

- Coupable : Thomas
- Lieu : salle informatique
- Horaire : 10 h
- Moyen d'accès : badge

Les indices sont ensuite générés et leur capacité à garantir
une solution unique est vérifiée.

#### Complexité

Soit n le nombre de variables, d la taille maximale
des domaines et k le nombre d'indices.

- Backtracking : O(d^n) en temps dans le pire des cas,
  hors coût de vérification des contraintes.
- Mémoire auxiliaire : O(n) pour la récursion,
  hors stockage des domaines et des indices.
- Vérification exhaustive de l'unicité : O(k × d^n)
  dans le pire des cas, pour des contraintes de coût constant.

Le backtracking réduit l'espace exploré en éliminant
les affectations partielles incompatibles.

#### Structures de données

- Listes pour les domaines et les indices.
- Ensembles pour les autorisations et les présences.
- Enumérations pour les horaires, les accès et les opérateurs.
- Objets métier immuables.

#### Alternatives écartées

- Tirage aléatoire simple : risque de générer des combinaisons
  invalides et de multiplier les tentatives.
- Recherche exhaustive comme algorithme principal :
  absence d'élimination anticipée des branches.
- Minimisation des indices : prévue pour la v0.2.0.

### Impact sur les couches

- **BD** : migration `V2__generation_enquetes.sql`.
  Persistance des enquêtes, domaines, indices et solutions
  dans neuf tables relationnelles.

- **Back** : module `generation` en architecture hexagonale.
  - `domain` : modèle métier et algorithmes.
  - `application` : services et ports.
  - `adapter/out/persistence` : persistance JPA et JDBC.
  - `adapter/in/web` : contrôleur REST et DTO.
  - `config` : configuration Spring Boot.

- **API** :
  - `POST /api/v1/enquetes` : génération (201).
  - `GET /api/v1/enquetes/{id}` : consultation (200 ou 404).
  - 400 : requête invalide.
  - 422 : génération impossible.

  La solution secrète n'est pas incluse dans les réponses.

- **Front** : écran Angular accessible via `/generation`,
  permettant de générer une enquête et d'afficher ses données
  et ses indices.

### Critères d'acceptation

- [x] Le joueur peut générer une nouvelle enquête.
- [x] La solution respecte les contraintes métier.
- [x] Les indices sont compatibles avec la solution.
- [x] Chaque enquête possède exactement une solution.
- [x] L'enquête est enregistrée en base de données.
- [x] La solution secrète n'est pas exposée par l'API.
- [x] L'algorithme gère l'absence de solution.
- [x] La génération est reproductible avec une seed fixe.

### Limites connues

- Scénario et domaines prédéfinis dans l'API.
- Nombre limité de variables et de types d'indices.
- Nombre d'indices non minimal.
- Difficulté non contrôlée.
- Deux générations successives peuvent produire la même solution.
- Complexité exponentielle dans le pire des cas.
- Retour HTTP 422 non testé de bout en bout.

La minimisation des indices est prévue pour la v0.2.0
et la génération à difficulté cible pour la v1.0.0.
