## 1. Idéation

### Besoin
Une enquête est décrite par des variables (le coupable, le lieu, l'objet) et par des indices qui éliminent des possibilités. À la main, raisonner sur ces indices est long et source d'erreurs : le nombre de combinaisons croît vite (3 suspects × 3 lieux × 3 objets font déjà 27 scénarios) et les indices se répondent entre eux (éliminer un lieu peut éliminer un suspect, qui en élimine un autre).

Le moteur de déduction automatise ce raisonnement. À partir des indices saisis, il retire les valeurs devenues impossibles, détecte les indices contradictoires et indique si l'enquête a zéro, une ou plusieurs solutions. Il permet à un joueur de vérifier ses déductions et à un enseignant de contrôler qu'une enquête qu'il a écrite est solvable et sans ambiguïté.

### Scénarios d'usage
- *En tant que joueur ou joueuse*, je saisis des indices sur un incident **afin de** vérifier que l'enquête est solvable et possède exactement une solution (enseignant : je soumets mes propres contraintes).
- *En tant qu'enseignant*, j'envoie des indices contradictoires **afin d'être averti** que mon enquête n'a pas de solution, avant de la proposer aux étudiants.

### Modèle
Le module `solveur` définit son propre modèle, sans importer celui des autres features :

- **`Variable`** : un nom (ex. `Coupable`) et son **domaine**, l'ensemble des valeurs encore possibles.
- **`Contrainte`** : deux variables X et Y, une règle qui dit si un couple de valeurs `(vx, vy)` est compatible, et une description lisible. `inverse()` renvoie la même contrainte vue de Y vers X.
- **`Indice`** (interface scellée) et ses deux formes, qui décrivent les indices comme des données :
  - `Exclusion(variable, valeur)` : « la variable n'est pas cette valeur » ;
  - `Implication(variableX, valeurX, variableY, valeursAutoriseesY)` : « si X vaut `valeurX`, alors Y est parmi ces valeurs ».
- **`Resultat`** : le nombre de solutions (0, 1, ou 2 pour « plusieurs ») et les domaines restants par variable.

Invariants :
- Un domaine ne fait que diminuer pendant la propagation. Il ne grandit que lors d'une restauration explicite (retour arrière).
- Le domaine n'est modifié que par `retirer`, `fixer` et `restaurer` de `Variable` : `getDomaine()` renvoie une vue en lecture seule.
- Le constructeur de `Variable` copie l'ensemble reçu, et `sauvegarder()` renvoie une copie indépendante : modifier un domaine ne modifie jamais une sauvegarde.

Lien avec l'entité pivot : le moteur est volontairement indépendant. Son modèle est de la donnée brute (noms et valeurs), que l'intégration avec les autres features traduira. Le branchement est prévu en v0.2.0.

### Algorithme

**1. Propagation de contraintes (AC-3).**
Une valeur d'une variable X est **supportée** par une contrainte si, dans le domaine de Y, il existe au moins une valeur compatible avec elle. `revise(X, Y)` retire du domaine de X toute valeur sans support dans Y et renvoie `true` si le domaine a changé.

AC-3 range tous les arcs (chaque contrainte dans les deux sens) dans une file, puis répète : il prend un arc et appelle `revise`. Si le domaine de X a changé, les valeurs d'autres variables qui s'appuyaient sur X ont peut-être perdu leur support, donc les arcs qui pointent vers X sont remis dans la file. Si un domaine devient vide, l'enquête est incohérente et l'algorithme s'arrête avec un échec. Quand la file est vide, le problème est cohérent d'arc.

Exemple (enquête de référence) : `Coupable = {Alice, Bob, Chloé}`, `Lieu = {salle, imprimante, serveur}`, indice « le lieu n'est pas la salle » (ramène `Lieu` à `{imprimante, serveur}`), « Alice n'a accès qu'à la salle » et « Chloé n'a accès qu'à la salle ».
- `revise(Coupable, Lieu)` avec la règle d'Alice : Alice n'a aucun lieu compatible, elle est retirée ; Bob et Chloé restent (la règle ne les concerne pas). `Coupable` a changé : les arcs qui pointent vers lui sont remis dans la file.
- `revise(Coupable, Lieu)` avec la règle de Chloé : Chloé est retirée. `Coupable = {Bob}`.
- `revise(Lieu, Coupable)` : Bob est compatible avec les deux lieux, rien n'est retiré, la file se vide.
Résultat : `Coupable = {Bob}`, `Lieu = {imprimante, serveur}`.

**2. Pourquoi AC-3 ne suffit pas.**
AC-3 réduit les domaines mais ne choisit pas : ici `Lieu` reste à deux valeurs. Un domaine non vide ne prouve pas qu'il existe une solution complète, et des domaines à plusieurs valeurs ne disent pas combien il y en a. Pour compter les solutions et vérifier leur unicité, il faut explorer les choix.

**3. Retour arrière.**
`compterSolutions` fonctionne ainsi :
1. Lancer AC-3. En cas d'échec, ou si un domaine est vide : 0 solution.
2. Si tous les domaines sont des singletons : une solution complète, on renvoie 1.
3. Sinon, choisir une variable dont le domaine a plus d'une valeur. Pour chaque valeur de ce domaine : **sauvegarder** les domaines de toutes les variables, **fixer** la variable à cette valeur, **compter récursivement**, puis **restaurer** les domaines.
4. S'arrêter dès qu'on atteint 2 solutions.

La sauvegarde est indispensable : AC-3 retire des valeurs dans les `Variable` partagées. Sans restauration, les retraits d'un essai fausseraient les essais suivants. Le plafond à 2 suffit pour distinguer 0, 1 et « plusieurs », et évite d'énumérer toutes les solutions.

Suite de l'exemple : AC-3 a laissé `Lieu = {imprimante, serveur}`. Le retour arrière choisit `Lieu`, essaie `imprimante` (tous les domaines sont des singletons : 1 solution), restaure, essaie `serveur` (1 solution). Total 2 : l'enquête a **plusieurs** solutions. Si on ajoute l'indice « Bob n'a accès qu'à l'imprimante », AC-3 retire `serveur` de `Lieu` et il ne reste qu'une solution.

**4. Complexité et alternatives.**
- AC-3 : O(e · d³) en temps pour e arcs et des domaines d'au plus d valeurs (chaque arc peut être remis dans la file au plus d fois, et `revise` coûte O(d²)). Mémoire en O(e + n·d).
- Retour arrière : exponentiel au pire cas (d^n pour n variables), mais fortement élagué car AC-3 retire des valeurs avant chaque choix. La sauvegarde coûte O(n·d) par niveau de récursion.
- Alternative écartée : énumérer toutes les combinaisons puis vérifier chaque indice. Aucun élagage : le coût est toujours d^n, y compris quand une contradiction apparaît très tôt.
- Structures de données : `LinkedHashSet` pour les domaines (ordre stable, tests déterministes), `ArrayDeque` pour la file d'arcs, `Map` pour les sauvegardes.

### Impact sur les couches
- **BD** : aucune migration en v0.1.0. Le moteur est sans état : les indices arrivent dans la requête et le résultat est calculé à la volée, rien n'est stocké.
- **Back** : module `solveur`. `domain` : `Variable`, `Contrainte`, `Exclusion`, `Implication`, `Indice`, `Resultat`, `Ac3`, `RetourArriere`, `EnqueteInvalideException`, `EnqueteIncoherenteException`. `application` : port `ResoudreEnqueteUseCase` et service `ResoudreEnqueteService`. `adapter/in/web` : `DeductionController`, DTO, `ErreursWebHandler`. `config` : `SolveurConfiguration`.
- **API** : `POST /api/v1/deduction/resoudre` : 200 (résultat), 400 (variable ou type d'indice inconnu), 422 (indices contradictoires, aucune solution).
- **Front** : écran Angular avec un bouton « Résoudre l'enquête » qui affiche le nombre de solutions et les valeurs encore possibles par variable.

### Critères d'acceptation
- [x] Sur l'enquête de référence (Alice et Chloé n'ont accès qu'à la salle, la salle est exclue), `Coupable` est réduit à `{Bob}` et le résultat compte plusieurs solutions.
- [x] Avec une contrainte de plus sur Bob, l'enquête a exactement une solution.
- [x] Des indices contradictoires donnent un code 422.
- [x] Un indice sur une variable inconnue donne un code 400.
- [x] Le module `solveur` ne dépend d'aucun autre module.
- [x] `ArchitectureHexagonaleTest` reste vert.

### Limites connues
- Seules des contraintes binaires (entre deux variables) et des exclusions (sur une variable) sont gérées.
- Le comptage s'arrête à 2 : on distingue « 0 », « 1 » et « plusieurs », pas le nombre exact.
- Pas de persistance : les enquêtes ne sont pas sauvegardées.
- L'écran utilise une enquête fixe, sans formulaire de saisie.
- Pas encore branché sur le générateur d'affaires (F1) ni sur le filtrage d'hypothèses (F4) : l'intégration est prévue en v0.2.0.
- Pistes : formulaire de saisie des indices, explication de chaque déduction à partir de la description des contraintes, comptage exact des solutions.
