## 1. Idéation

### Besoin
Pour la création de cette feature, je me suis posé différentes questions :
- Quel est le probleme ? un joueur a une liste d'indices et veut savoir ce qui reste possible, cohérent ? 
En effet, lorsqu'on joue à un jeu d'enquete, les indices nous guide vers le résultat cohérent de l'enquete, donc la suite logique doit etre cohérente et le fil vert de notre algorithme doit etre également bon 

- Pourquoi le nombre de possibilités est compliqué à imaginer a la main? 
En fonction des conditions et des indices on a une matrice de solution qui diminue en grandeur, grace a mon algo on a une liste de possibilité cohérente avec les indices données.

- Que fait l'outil que j'ai réalisé ? 
Il vient detecter les contradictions, les valeurs qui sont impossibles et/ou incorrecte et vient nous guider vers une solution unique ou pas.

### Modèle
- Variable : un nom (par exemple : "Coupable" ou "Lieu") et une liste de l'ensemble des valeurs possible que j'ai appelé domaine. 
- Contrainte : On prend deux Variables et une règle qui définit la compatibilités des valeurs, suivi d'une description détaillé. 
- Indices du domaine : Exclusion("La variable n'est pas cette valeur") et Implication("Si X vaut a, alors Y est parmis les domaines de a").
- Resultat : Le nombre de solutions (0, 1, 2 pour "plusieurs" ) et les domaines restants.
- Invariants : je sais pas
- Lien avec l'entité pivot : je ne sais pas

     3. Retour arrière
        - Principe : choisir une variable à plusieurs valeurs, essayer chaque valeur, propager avec AC-3, annuler.
        - Pourquoi sauvegarder tous les domaines avant chaque essai, et les restaurer après ?
        - Pourquoi s'arrêter à 2 solutions ?
        - Déroule l'enquête de référence en entier (tableau ou liste d'étapes).

     4. Complexité et alternatives
        - AC-3 : O(e · d³) en temps pour e arcs et d valeurs par domaine (à justifier brièvement).

        - Alternative écartée : énumérer toutes les combinaisons sans élagage, et pourquoi.

### Impact sur les couches
- **BD** : aucune migration en v0.1.0. Le moteur est sans état : les indices arrivent dans la requête et le résultat est calculé à la volée, rien n'est stocké.
- **Back** : module `solveur`. `domain` : `Variable`, `Contrainte`, `Exclusion`, `Implication`, `Indice`, `Resultat`, `Ac3`, `RetourArriere`, `EnqueteInvalideException`, `EnqueteIncoherenteException`. `application` : port `ResoudreEnqueteUseCase` et service `ResoudreEnqueteService`. `adapter/in/web` : `DeductionController`, DTO, `ErreursWebHandler`. `config` : `SolveurConfiguration`.
- **API** : `POST /api/v1/deduction/resoudre` : 200 (résultat), 400 (variable ou type d'indice inconnu), 422 (indices contradictoires, aucune solution).
- **Front** : écran Angular avec un bouton « Résoudre l'enquête » qui affiche le nombre de solutions et les valeurs encore possibles par variable.

### Critères d'acceptation
- [x] Sur l'enquête de référence (Alice et Chloé n'ont accès qu'à la salle, la salle est exclue), `Coupable` est réduit à `{Bob}` et le résultat compte plusieurs solutions.
- [x] Avec une contrainte de plus sur Bob, l'enquête a exactement une solution.
- [x] Des indices contradictoires donnent un code 422.
- [x] Un indice sur une variable inconnue donne un code 400.
- [x] Le module `solveur` ne dépend d'aucun autre module.
- [x] `ArchitectureHexagonaleTest` reste vert.

### Limites connues
- Seules des contraintes binaires (entre deux variables) et des exclusions (sur une variable) sont gérées.
- Le comptage s'arrête à 2 : on distingue « 0 », « 1 » et « plusieurs », pas le nombre exact.
- Pas de persistance : les enquêtes ne sont pas sauvegardées.
- L'écran utilise une enquête fixe, sans formulaire de saisie.
- Pas encore branché sur le générateur d'affaires (F1) : l'intégration est prévue en v0.2.0.
